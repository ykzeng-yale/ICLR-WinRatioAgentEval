## Blocking finding: an unmatched receipt can clear the decision gate

In `experiments/live_ab/lab_orchestrator.py`, `World._anchor_request()` returns `None` when a receipt's `request_id` is absent from the in-memory and durable request spool. `World.ingest_receipts()` then assigns that row to `self.anchor_seq` (the newest anchor) rather than rejecting its attribution. For an `ok` row it chains an `anchor_receipt` under that sequence, carrying any supplied `created_at`. If the newest anchor is the blocking decision anchor, `lab_eventlog.decision_receipt()` treats this row as the decision's external receipt because it checks matching `anchor_seq` and server time, not the originating request ID. In `ANCHOR_BLOCK`, `decision_receipted()` is checked before the pending-anchor branch and can permit `traffic_switch` and post-decision dispatch. The normal anchor producer includes request IDs, but an unknown/stale/malformed spool row is currently not refused. A source-path witness suffices to reject the claimed gate; I have not claimed an end-to-end live execution or tested the owner host.

This is an **implementation integrity failure**, not an inference theorem or a reason to change the statistical rule. The partial new restart-cap case logic is received, not independently accepted.
