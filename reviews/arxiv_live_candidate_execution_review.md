## Concrete provenance findings

### E1 — Count unreturned interrupted requests as unknown usage

`lab_orchestrator.py:269-303` increments `unknown_usage_calls` only for `llm_error` events. A durable `llm_request` with no response/error is expressly permitted after `worker_died`, `episode_timeout`, or `interrupted` (`lab_verify_log.py:463-474`). The terminal reconstruction writes an `episode_revealed`, without creating an `llm_error` for that outstanding request (`lab_orchestrator.py:1874-1902`). Thus an interrupted request with unknown consumed tokens can produce **zero** unknown-usage calls.

The verifier's recount repeats this omission (`lab_verify_log.py:867-898`), so byte-equality of the two ledgers cannot detect it. `probe_ledger_seed.py` supplies one started request and a terminal worker-death reveal to both pure recount functions: each reports `unknown_usage_calls = 0`, with equal ledgers; exact output is saved in `probe_ledger_seed.json`.

**Required repair:** derive unknown usage by request ID from started requests lacking a complete known-usage terminal receipt, including interrupted pending requests; do not turn missing usage into zero tokens consumed. Avoid double counting explicit errors/retries. Add a fixture spanning request-start → worker death/resume → terminal reveal, and check the independently specified expected ledger. This affects resource-accounting provenance, not the score or confidence-band theorem.

### E2 — Prior-program seed persistence/checking is not implemented as described

Jobs point to `<trial work>/used_seeds.json` (`lab_orchestrator.py:1249`), and each one-episode worker loads it (`lab_worker.py:509`). The complete candidate implementation contains **no writer** for this file. Missing files silently produce an empty set (`lab_client.py:367-384`). The in-memory set therefore protects repeats only within one client episode. The per-trial verifier checks only its own `llm_request` events (`lab_verify_log.py:480-488`); `verify_program()` does not combine seeds across trials (`lab_verify_log.py:914-963`). This does not satisfy the prior-program-state wording of protocol §5.5 (`design/protocol_FINAL.md:898-901`) or the across-program check in the architecture.

The bounded probe initializes the absent seed state twice, forces the same entropy value, and obtains seeds `[42, 42]`. This is a deterministic demonstration of absent persistence, **not** an estimate of random-collision frequency. Worker-index parity still separates the two simultaneous slots; no arm-dependent coin/seed coupling is alleged.

**Required repair:** persist or reconstruct an auditable program-wide seed registry before starting successive episodes/trials and on resume, and check uniqueness across trial chains. If the design intentionally permits duplicates, correct the promise and report observed collision defects rather than claiming prevention. The protocol itself classifies collisions as a plumbing **DEFECT**, not trial invalidation; preserve that calibrated interpretation.

### E3 — Propagate the recorded cadence ruling and repair T4 resume payloads

`plan_resume()` counts unique chain-valid coins, not pre-coin enrollment records (`lab_orchestrator.py:648`); `_w_draw_coin()` takes the enrollment look immediately after durable randomization (`:1765-1774`). The crash fixture confirms a pre-coin `pair_enrolled` owns no monitored position. This is the appropriate implementation distinction, but the protocol/state-machine wording must consistently specify the same moment. The owner already documents conflicting wording and a verifier that compares look counts/values without fully pinning each look's event position (`IMPLEMENTATION_STATUS.md:194-228`). Propagate the recorded coordinator ruling consistently and test the intended event ordering before freeze; this review does not claim to have independently proved every cadence property.

The T4 canonical payload retains `inv` (`lab_worker.py:54-56,110`; orchestrator job field `:1220`), so a pair split across invocations can fail A/A byte identity even though the scientific configuration is unchanged. The candidate explicitly retains a passing test that demonstrates this **verifier failure** (`tests_lab_e2e.py:462`, exact test name `test_t4_payload_identity_breaks_when_a_pair_spans_two_invocations`; status `:255-264`). The test passed here, reproducing the known defect rather than resolving it. Repair the canonical exclusion list consistently in the protocol, worker, orchestrator, verifier, and fixtures; confirm same-configuration resumed T4 passes while genuine configuration drift still fails.

### E4 — Clarify what is durable before POST

Protocol §5.5 says the seed is written to both worker spool and `llm_request` before POST (`protocol_FINAL.md:900-901`). The client durably writes `call_started` before the HTTP request (`lab_client.py:507-532`), whereas the orchestrator later projects the spool into `llm_request` (`lab_orchestrator.py:1340-1396`). No chain-acknowledgment handshake occurs before the client POST. The durable spool provides useful write-ahead evidence; the documentation should distinguish that guarantee from asynchronously chained ingestion. If a pre-POST chain event is actually required, implement and test acknowledgment rather than claiming it already exists.
