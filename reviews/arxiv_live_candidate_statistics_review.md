## 1. Required scientific-text correction: abstention has not been established

**Verified locations:** `design/protocol_FINAL.md:178` retains the heading “guaranteed-abstention deploy route”; lines 203–207 retain “the unreachability result below is untouched”; lines 237–249 use the same-task pilot standard error 0.0151 to call deployment a “PRE-SPECIFIED NEAR-CERTAIN ABSTENTION” and describe the expected scientific content as the composite crossing while the success guardrail refuses. Lines 301–302 again say the data cannot reach the margin at this horizon. The analogous declaration also remains at line 88 and the report template at lines 293–298. The acknowledged correction at lines 239–242 explicitly disclaims logical impossibility, but it does not resolve these surviving active statements. The owner withdrawal comment was already received at 01:52:23 UTC, before candidate head `5776877` at 02:16 UTC, as established by root's chronology check. The active document at this reviewed pin still retains these statements despite that withdrawal; the acknowledged correction needs to be propagated into the document.

For fully revealed data the success condition is

`mean(D) > r(n) - .03`, with `r(n) = sqrt((n+100) log((n+100)/(100*.00625^2)))/n`.

The independent arithmetic gives `r(568)=0.1579515124940428`, so the required observed contrast at 568 is strictly above `0.1279515124940428`. If the observed difference is exactly zero, the first integer at which `r(n)<.03` is 17,097. These are conditional threshold calculations, not a power analysis. With pending outcomes replace the mean by the mean lower score enclosure; this cannot make the gate less conservative.

A feasible counterexample to guaranteed abstention is 100 fully resolved pairs with candidate success one and incumbent success zero. Both scores are one. Both lower endpoints are `0.5343070794820347`, and **both the live implementation and independent reference path permit deployment**. Thus the present code does not hard-code the erroneous textual impossibility claim.

The newer “8.5 paired standard errors” argument also uses an inappropriate uncertainty scale. The same-task paired pilot SE does not describe this trial's pairs of different tasks, with one task assigned to each arm. The protocol's own cross-task planning table (`:209–218`) gives `P(D=+1)=P(D=-1)=.1961`, hence variance approximately `.3922`. If one made an explicitly hypothetical iid cross-task approximation, its horizon SE would be `sqrt(.3922/568)=.0262772326881` and the `.1279515` threshold would be approximately **4.869 such SE**, rather than 8.5. This is a diagnostic showing why the quoted calculation does not transfer; **4.869 is not a replacement calibrated power calculation**. The actual fixed roster, within-stratum pairing, sequential looks, history dependence, new runtime and new S2 tasks are not represented by that iid approximation. The many cross-task pilot comparisons share underlying trajectories and are not independent replications.

**Concrete repair without changing the design:** replace the declarations with:

> This is a prospective feasibility study. At 568 completely observed pairs the declared success gate requires an observed success difference above 0.1279515; if the observed difference stays zero, the gate cannot pass within this horizon. These calculations suggest limited sensitivity near zero but do not calibrate the probability of deployment or abstention for the prospective design. Deployment, harm and no decision are all retained and reported under the frozen rule. Whether either component crosses is an empirical outcome.

Keep `.03`, the horizon and the existing decision rule. Remove “guaranteed,” “unreachability,” “near-certain,” the 8.5-SE rationale and deterministic outcome language throughout active claims/templates. If a future report wants a quantitative prospective crossing probability, it needs a clearly specified, design-matched planning distribution and Monte Carlo uncertainty; that is not required simply to retain an honest feasibility study.

## 2. Verified statistical implementation on the inspected paths

**Formula and error allocation.** `lab_monitor.py:230–264` calls the pinned `normal_mixture_radius` with `variance_process=n`, uses the sum of lower/upper score enclosures divided by the full enrolled `n`, and intersects with the known score range. `src/winstats.py:51–61` matches the displayed formula. Its independently exported SHA-256 is `56955ce09a8ac7afb15f2bd251048537eabcc04ea75e7579bdb825594f41fc69`, as required by the config. The two-sided band already includes both tails; four trials times two bands times `.00625` equals `.05`. The union-bound interpretation in protocol `:1460–1508` does not require trials to be independent. No extra allocation is needed merely to inspect both upper and lower endpoints of the same band. This does not authorize extra primary hierarchies, strata, models or decision rules.

For bounded adapted scores, Hoeffding's conditional mgf bound supplies variance proxy one per pair. Normal mixing yields a two-sided bound for the sum of centered scores and therefore for the running average of their history-conditional means. Valid partial enclosures contain the complete-score band pathwise at the same index. This gives simultaneous calendar-display coverage through the enrollment-order coverage event, rather than by claiming that partial traces themselves are an e-process. This reasoning requires the stated adaptedness and valid endpoint/certificate premises. It is neither iid inference nor a confidence statement about the entire finite roster or future traffic.

**Randomized prefix and same-look gates.** The live replay stages `pair_enrolled` without creating a statistical observation (`lab_monitor.py:670–677`); only `coin_drawn` increments the prefix (`:679–696`). The reference rule independently does the same (`lab_reference_rule.py:322–368`). A staged pair without a coin produces no look. `MonitorState.enroll`, `sums` and `bands` preserve every randomized position (`lab_monitor.py:325–394`). `decide` uses only current bands, strict `U_h<0` for harm and strict `L_h>0` jointly with `L_s>-.03` for deployment (`:511–550`). Equality does not cross. A completed-prefix readout exists but is not the decision input. A reviewer witness passes deployment at 100 complete pairs with 44 success differences of +1 and 56 of zero, then loses the success gate after adding one unresolved pair: at 101 the success sum bounds are [43,45] and the lower band is `-.0365970847426561`. The earlier passing gate is not retained.

**Comparator and partial outcomes.** Complete scores use success first, latency second with relative tolerance .05, and cost eligibility only on joint success (`lab_enclosure.py:370–394`). Joint failures tie regardless of latency. Exact 95-versus-100 latency equality ties. The success enclosure is the difference of feasible binary-success bounds (`:426–445`). A revealed successful episode of latency `a` certainly beats its pending partner when `.95*ell > a+1e-9` (`:448–497`): failure of the partner loses at success; success of the partner loses at latency. The success difference remains unresolved (`:500–520`). The extra positive epsilon is conservative. These certificates require `ell` genuinely to lower-bound the final endpoint; the module derives it from monotonic worker stamps (`:397–420`), but this review does not establish live clock or endpoint receipt integrity.

**Design and causal scope.** `lab_design.py:52–84` deterministically permutes tasks within strata, forms disjoint pairs within each stratum, then permutes whole pairs. It contains no assignment-coin generation. With stratum sizes 3 and 5, the independent fixture returns three pairs and two leftovers, reproducibly and without task reuse. This agrees with the at-most-568 arithmetic conditional on final eligible roster sizes. The protocol explicitly permits history dependence and uses `E(score_i | F_{i-1})`, with later coins absent while earlier pairs run (`protocol_FINAL.md:1192–1241`). This supplies a coherent intended model, conditional on its physical implementation and fresh label-blind randomization. I did not independently verify the complete scheduler/coin/host implementation. One unresolved pair at a time is a narrow live feasibility setting, not broad empirical validation under cross-pair delayed completion. The document appropriately distinguishes this scope at `:1521–1525`.

## 3. Defensive clipping contract accepts an invalid known range

**Verified location:** `lab_monitor.py:133–134` accepts any `-1 <= clip_lo < clip_hi <= 1`, although its error message says the clip is frozen at `[-1,1]`; `from_config` forwards the values (`:169–199`). Intersecting with a smaller range is valid only if it is actually known to contain the target. No such extra restriction is justified here.

**Reproducible witness:** change only the fixture config's clip to `[.2,1]`. `MonitorConfig.from_config` accepts it. At 100 complete zero-score pairs both reported lower bounds become `.2`, and `decide` returns `deploy_candidate`, falsely excluding the possible target zero. The independent reference hard-codes `[-1,1]`, so a correctly enforced shadow comparison should detect this altered configuration; the live helper itself nevertheless violates its advertised fail-closed contract.

**Scope and remedy:** the actual pinned config uses `[-1,1]`, so this witness does **not** establish an activated numerical error in the reviewed frozen rule. Enforce exact equality to `(-1.,1.)` in the live configuration validator and add a rejection fixture before freeze. Do not infer that arbitrary altered configs carry the stated guarantee.
