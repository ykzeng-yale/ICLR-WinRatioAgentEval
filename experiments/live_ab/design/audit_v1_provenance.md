## Verdict: BLOCK

Two rules of v1 cannot be frozen as written: the anchoring scheme does not deliver the chronology bound the protocol claims for it (finding 1), and the abort/re-run rule is a fresh-seed redraw of outcomes that can already be determined, contrary to R2 items 32, 52, 53 (finding 2). Neither touches the statistical rule of section 8; both need a rewritten rule and a re-audit of the rewritten text. Seventeen further findings are MAJOR (must be closed before the freeze, no redesign) and six are MINOR.

Severity scale used here. BLOCKER: as written, the rule contradicts a root-derived constraint or makes a claim of section 1.3 unsupportable; the rule must be redesigned and re-audited. MAJOR: a specification gap, an unverifiable step or an internal contradiction that must be closed before the freeze. MINOR: tightening.

## BLOCKER findings

### 1. BLOCKER — The anchoring scheme does not bound the rewrite window it claims to bound

**Passages.**
- 4.3: "anchors (local commit, push, issue comment) bound the window in which a rewrite is possible to at most 25 pairs or 10 minutes".
- 11.4: "Triggers: `trial_started`; every 25 completed pairs or 10 minutes, whichever comes first; every `decision`; every `amendment`; `trial_ended`. ... At freeze, trial start, decision, amendment and trial end it also posts an issue comment containing `upto_h`; the comment's server-side `created_at` is the external timestamp. Local commit times are client-side and are never cited as evidence".
- 11.4: "Anchoring never blocks a trial (`anchor_failed` is logged; the report lists the longest unanchored span), with one exception: an amendment cannot take effect without its external receipt".
- 11.3: "Prototype (`eventlog_proto.py`): tampering, deletion and a wrong genesis are detected".
- 1.3 item 1: "internally frozen, publicly timestamped"; item 3: "the rule crossed at enrolled pair n at calendar time t".

**Why it fails.**
1. The chain is an unkeyed SHA-256 chain over a plaintext file. Whoever holds the file can delete or replace any suffix and recompute every later `h` in milliseconds. "Tampering detected" in the prototype means only "tampering by someone who does not recompute the chain". By itself the chain proves nothing against the operator; all evidential weight sits on the external anchors.
2. By the protocol's own definition the only external timestamp is an issue comment's `created_at`, and comments are posted at five events only. Periodic anchors are commit + push. The commit time is client-side (the protocol says so) and a push returns no server timestamp that the protocol captures, cites or deposits. Therefore the externally timestamped windows are freeze -> trial start -> decision -> end. In T1 the window "trial start -> decision" is the whole randomized phase (planning quartiles 170 / 280 / 395 pairs), not 25 pairs.
3. An anchor is an upper bound on creation time ("this prefix existed no later than S"). Nothing in a periodic anchor gives a lower bound: the `anchor_receipt` of a push contains a commit id, which the operator computes himself, and no server-assigned value. So nothing shows that the events after anchor k were produced after anchor k.
4. Start and decision anchors do not block. A trial can draw its first coin before any external record of `trial_started` exists; a private run that is abandoned before the first comment leaves no trace. A `decision` whose anchor fails has only a client-side time, which is the airline finding again ("decision time had no immutable record").
5. No check compares externally measured elapsed time with logged time, and `trial_paused` admits the reason "operator unavailable", an unverifiable gap of any length.

**Concrete scenario (T1, first-crossing rule, no retained crossings).** The `monitor_update` lines in the plaintext log show the S-gate log E at 2.9 against the threshold log 25 = 3.22 at pair 299, drifting down. The operator stops the orchestrator, deletes the log back to the last pushed anchor (pair 275), recomputes nothing (the prefix is intact), and resumes: 24 pairs get new coins and new generations. He repeats until the gate crosses. Each repetition costs about 6 minutes. The published log verifies; the pushes are consistent because a push of a rewritten suffix after the same anchored prefix is a fast-forward; no issue comment exists between start and decision; commit times are not evidence. Because the decision is taken at the first crossing at any look, a per-window redraw is a steering device for the one gate whose crossing is uncertain. The same device suppresses a T4 false crossing or a T1 `RETAIN`.

**What git anchoring actually proves, and how often it is needed.** It proves that the bytes with head `upto_h` existed no later than the moment GitHub received them, and only to someone who can read that repository and only if that server time is recorded somewhere citable. It does not prove that events happened at their `t_wall_ns`, that this is the only log of the trial, that nothing was removed before the anchor, that coins came from `os.urandom`, or that the producing code was the frozen harness (the harness hashes in the log are self-asserted). Frequency is secondary: without server timestamps, lower-bound tokens and an elapsed-time audit, even per-pair pushes would not reveal a redraw; with them, the stated cadence (25 pairs or 10 minutes) is adequate. What must block is fixed by irreversibility, not by cadence: freeze before the first design episode, `trial_started` before the first coin, `decision` before the first post-decision dispatch, amendments before they take effect.

**Required change.**
(a) Every anchor, periodic ones included, must obtain a server-side timestamp tied to the chain head: after the push, create a commit comment on the pushed commit (or an issue comment) whose body contains `upto_seq`, `upto_h` and the log-prefix SHA-256; store the API response fields `id`, `node_id`, `created_at`, `updated_at` and the SHA-256 of the raw response in `anchor_receipt`.
(b) Lower bound: `anchor_receipt` (with the server-assigned `id` and `created_at`) is chained, so every later event provably postdates that comment. State this property and have the verifier check it.
(c) Blocking anchors: the first `coin_drawn` of a trial requires the chained receipt of the `trial_started` anchor; the first `arm_assigned_by_decision` requires the chained receipt of the `decision` anchor (bounded wait with retries; on final failure proceed, log `anchor_failed`, and the report replaces "calendar time t" in claim 3 by "client clock, not externally timestamped"). Report switch latency both to `traffic_switch` and to first dispatch.
(d) Time-sandwich audit in `lab_verify_log.py`: for consecutive external receipts k, k+1 compare `created_at` difference with the `t_wall_ns` difference of the corresponding `anchor` events (tolerance frozen, e.g. 30 s), and tabulate every intra-window gap above 5 s between consecutive events together with every invocation boundary (last event type before the boundary, open attempts, whether a `coin_drawn` was the last durable event). A discarded window then shows either as an unexplained gap (genuine clock) or as a sandwich violation (falsified clock). Both tables go into the report for every trial.
(e) Pauses: `trial_paused` and `trial_resumed` each require an external receipt; remove "operator unavailable" or require that the pause was anchored before the operator left.
(f) Rewrite 4.3 and 1.3: state what the anchors prove and what they do not (the list above). Delete "bound the window ... to at most 25 pairs or 10 minutes" unless (a) to (d) are implemented. Under the C10 fallback (local commits only) the run has no external chronology at all after the freeze; say exactly that, not only "wording is dropped".
(g) Provide an operator-independent proof for the four critical heads (freeze bundle, trial start, decision, end), for example OpenTimestamps or an RFC 3161 token stored in `anchors/`, so that chronology does not depend on a comment that the account owner can edit or delete (see finding 16). This needs a user approval item next to C10.

### 2. BLOCKER — Re-running an aborted attempt is a fresh-seed redraw

**Passages.**
- D19: "An attempt that never returned is re-run under the SAME arm (max 3 attempts, then scored as failure)."
- 5.4: `idx = ((((e * 4096 + arrival) * 4 + attempt) * 8 + call_index) * 4 + try_index)` (the attempt index enters the seed, so a re-run samples anew).
- 5.5: "`episode_hard_cap_s` | 1,800 | watchdog; exceeding it is handled as a dead worker (6.4 row 10)"; "`max_attempts` | 3".
- 6.4 row 10: "worker dies, or `episode_hard_cap_s` exceeded (worker killed) | `attempt_aborted`; new worker; same arrival, same arm, `attempt + 1`".
- 6.4 row 11: "orchestrator crash, power loss, operator stop | resume per 12.3; every open attempt gets `attempt_aborted(orchestrator_restart)` and is re-run under the same arm".
- 11.2 #15: "reason (worker_died / hard_cap / orchestrator_restart / operator_stop)"; against 12.4: "A trial may be paused only between pairs".
- 12.3 step 2: "else `attempt_aborted` and re-run under the same arm".

**Why it fails.**
1. For `single_shot` the outcome is determined the moment the single response arrives: verification of a fixed program is deterministic up to timeouts. The response body is on disk (`requests/<request_id>.json.gz`) and its `llm_response` is in the log before verification starts. A worker death, an orchestrator crash or an operator stop during the verification window (up to 10 s wall, longer under load) discards that determined outcome and replaces it by a new sample with new seeds. R3 itself calls the analogous act "a second draw that an observer could suspect of being outcome-dependent" when it justifies orphan recovery; the same reasoning applies one step earlier, before the record file exists.
2. Scenario: the operator (or a watchdog script) reads the candidate's response, sees a wrong program, sends SIGKILL to the worker. The log shows `attempt_aborted(worker_died)` and a second attempt; the arrival now succeeds with probability 1 - (1 - p)^3 instead of p. The only trace is a reason code that the protocol lists as routine. In T1 this is the cheapest way to move the uncertain S gate.
3. Arm dependence without any malice. With `request_timeout_s >= 180`, three tries and four calls, a legitimate `self_test_repair` attempt can last 4 x (180 + 2 + 180 + 4 + 179) s = 2,180 s plus restart waits of up to `server_recovery_s` per try, which exceeds the 1,800 s cap; a `single_shot` attempt is bounded by about 546 s and can never reach the cap. The cap therefore converts slow failures into fresh draws in one arm only. In T1 and T2 that arm is one of the two compared systems.
4. It contradicts the root-derived checklist that the protocol says it implements: R2 item 32 ("each episode has a frozen hard timeout so a pending pair has a known worst-case score (timeout = failure)"), item 52 ("No episode-level retry (or exactly one, frozen, arm-blind); the canonical record is the first attempt"), item 53 ("in-flight episodes at a crash are recorded as `INTERRUPTED` and scored by the frozen failure rule"), and R1 e.4 item 3 ("never re-run for a better outcome"). `prop:delay`'s text treats failure to reach the outcome by the horizon as an endpoint.
5. Internal contradiction: 12.4 allows pauses only between pairs, yet `operator_stop` is a listed abort reason with a re-run.

**Required change.**
(a) No fresh sampling for any call that was already answered. Workers persist every response to a worker-local, fsynced, append-only spool before using it (this spool is also required by finding 7). A continuation of an interrupted attempt replays the stored responses byte-identically (matched by arrival, `call_index` and messages hash) and issues only calls that were never answered; if the messages hash of a replayed call differs, the arrival is revealed as `success = 0`, `error_class = harness_abort`. The `attempt` index leaves the seed rule for answered calls.
(b) `episode_hard_cap_s` is a frozen horizon: exceeding it is a terminal outcome (`success = 0`, `error_class = hard_cap`, `latency_s` = cap), never a re-run. Set the cap from the calibration by a written rule so that it exceeds the provable maximum duration of a legitimate attempt of either workflow, or state that it binds on one workflow only and report how often it bound, by arm.
(c) Remove `operator_stop` as an abort reason. A graceful stop drains the in-flight pair and then pauses; anything else is a crash and is labelled as one.
(d) If (a) is judged too costly, the only acceptable alternative is `max_attempts = 1` with every non-returned attempt revealed as `harness_abort` failure, plus a frozen rule for a pair interrupted by an orchestrator crash (state whether an episode already revealed keeps its outcome; note that under this alternative a crash while the slow arm is still running scores the slow arm as failed, so the asymmetry must be disclosed and the per-arm abort table of (e) becomes primary reporting). A fresh-seed re-run is not acceptable in any variant.
(e) Report, per trial and arm: aborted attempts by cause, the number of `llm_response` events already logged for each aborted attempt, and whether the final outcome differed from what the logged responses determined.

## MAJOR findings

### 3. MAJOR — The coin is operator-attested; the mitigations offered for that are void

**Passages.** 4.2: `raw = os.urandom(8)`, `"raw_hex": raw.hex()`. 4.3 table row (c): "Rejected: needs network calls during the run; policy is loopback only." 4.3: "`llama-server`'s own timestamped log and the server token counters (11.5) would show requests that are absent from the event log; operator actions are logged events; the operator console shows no arm-level outcome summary before the decision event." 1.3 item 1: "physically randomized (fresh OS-entropy coin per arrival pair, logged before execution)". 4.3: "A preflight self-test draws 10,000 non-design coins".

**Why it fails.** (i) `raw_hex` is unverifiable decoration: a fabricated log carries fabricated hex, and 63 of the 64 logged bits are unused. The 10,000-draw self-test says nothing about the design coins. An outsider cannot distinguish a genuine stream from a chosen one. (ii) The kill-after-coin path that 4.3 concedes costs no measurable time (no episode is run), so neither anchors nor the time audit of finding 1 detect it; with the frozen harness the only trace is an invocation boundary whose last durable event is `coin_drawn`, and the protocol prescribes no report of such boundaries. (iii) The server log is a plain file under `<WORK>`, unchained and unanchored; the token counters reset at every server restart. Neither is an independent witness. (iv) Console blindness is irrelevant: `events.jsonl` is plaintext with the `bit` and the task uids, and the operator is the same agent session that tails logs (finding 20). (v) Row (c) is rejected for "network calls during the run", yet D20 makes network calls during the run; the rejection reason is inconsistent. Coin-only manipulation matters because within strata `S1_k1` and `S2` the pilot tells which task of a pair is easier for which workflow, and under finding 12 a rehearsal tells it almost exactly.

**Required change.** (a) Claim 1.3 item 1 and every derived sentence carry "operator-attested; not independently verifiable" next to "OS-entropy coin", and section 7.4's assumption "the operator does not act on coins" is repeated wherever the fair-coin reading is used. (b) Forensics that cost nothing: the verifier tabulates every invocation boundary with the last durable event and open attempts; any boundary directly after a `coin_drawn` with no `episode_started`, any torn region that parses as (or is a prefix of) a `coin_drawn`, and any `log_recovery` without a change of `kern.boottime` between the two invocations (a single `os.write` cannot be torn by a process kill) is listed as an integrity event; a frozen rule states from how many such events on a trial is labelled "integrity-qualified" in every table (suggest 1 for coin-adjacent events). A torn region that is not a strict byte prefix of a canonical event is reported as evidence of editing. (c) Report the distribution of `episode_started.t_mono - coin_drawn.t_mono` and flag gaps above 1 s. (d) Each anchor records byte length and SHA-256 of `llama_<port>.log`, and the verifier checks that each anchored log prefix is a prefix of the next. (e) Either correct the reason for rejecting a public beacon or put the option to the coordinator as a CONFIRM item: a beacon-derived coin with a round rule fixed in advance is the only construction here that removes reliance on the operator, and future coins would still not exist at dispatch. If the coordinator keeps OS entropy (the fixed design intent), (a) to (d) stand.

### 4. MAJOR — "Durable coin" is ambiguous on resume; the torn-tail rule can dead-end the chain

**Passages.** 4.2 (v): "on resume a durable coin is reused, and a torn (non-durable) coin line can never have been acted on because dispatch requires the completed fsync". 12.3 step 2: "no durable coin -> it is simply the next pair". 11.3: "A byte run that fails verification is legal only as the last line of a file being opened for resume, or when the next valid event is a `log_recovery` committing to exactly those bytes." `eventlog_proto.py:78-79` raises on "two consecutive invalid lines".

**Why it fails.** 4.2 equates "torn" with "non-durable". They differ. SIGKILL between `os.write` and the return of `F_FULLFSYNC` leaves a complete, chain-valid `coin_drawn` line in the page cache, which the kernel persists. The bit was readable on disk. An implementer who reads "no durable coin -> next pair" as "no coin whose fsync was confirmed" voids the line and draws again: a redrawn coin after a crash, which is the exact path the brief asks about. Second, non-durable events (`llm_request`, `llm_response`, `monitor_update`, several KB each) can leave a torn region that spans more than one line after a power loss; the rule "legal only as the last line" and the prototype's "two consecutive invalid lines" then make the log unverifiable for ever, resume refuses, and not even `trial_aborted` can be appended. The protocol has no rule for a trial whose chain cannot be opened.

**Required change.** State: "every chain-valid `coin_drawn` line present in the file is binding on resume, whether or not its fsync had returned; a coin is void only if its line fails verification." Define the torn region as all bytes from the first invalid byte to end of file, committed as one opaque region (offset, length, SHA-256) irrespective of newlines inside. Add kill-point tests for "after write, before fsync return" and for a multi-line torn tail. Add the rule for an unopenable chain (trial closed by an external anchored statement; nothing re-run).

### 5. MAJOR — Resume is undefined for the post-decision phase and around `decision`

**Passages.** 12.3 step 2 speaks only of pairs and coins ("durable coin with a missing reveal -> ..."). Step 3: "Rebuild the monitor by replay. If a `decision` exists, the phase is restored and no coin is ever drawn again." 8.7: "appends `decision` (durable), requests an immediate anchor, appends `traffic_switch`". 8.2: "No retained crossing: only the current prefix counts".

**Why it fails.** (i) Post-decision arrivals carry `arm_assigned_by_decision`, not a coin, and run work-conserving; the text gives no rule for such an arrival with a missing reveal, nor for leftovers. (ii) Crash after the second `episode_revealed` of look n (durable) and before `decision` (the `monitor_update` between them is non-durable): step 3 restores a phase only "if a `decision` exists". An implementation that continues with pair n+1 loses a crossing that the frozen rule had reached, and because crossings are not retained the trial's decision then depends on a crash. (iii) Crash between `decision` and `traffic_switch`, and a duplicate `pair_enrolled` after a crash between `pair_enrolled` and `coin_drawn`, are unspecified.

**Required change.** Resume replays every look from `n_min` to `N_c`; if the replay finds the first crossing at n* and no durable `decision`, it appends `decision` for n* (flag `decided_on_resume`, with both times) before anything else; if a `coin_drawn` exists for a pair beyond n*, `trial_aborted(harness_defect)`. Extend step 2 to assignment events of either kind. Add invariants: no `pair_enrolled` for pair n+1 before the reveal-triggered look n was evaluated; at most one `pair_enrolled` per pair per invocation, re-enrollment after a crash flagged. Add these windows to the kill-point tests of Appendix C (R3 lists eight; none lies between the second reveal and `decision`, or after `traffic_switch`).

### 6. MAJOR — Monitor fix versus drift refusal; no rule for a replay mismatch

**Passages.** 6.4 row 17: "after an amendment (12.2) the monitor is replayed from the log". 12.3 step 1: "refuse on any drift against `trial_started`". 12.1 step 6: "re-verifies harness, config, binary and weights at every invocation". 12.2: monitoring parameters "cannot be amended within a trial". 9.2: "the recomputation must reproduce every `monitor_update` and the `decision` exactly."

**Why it fails.** A fix of `lab_monitor.py` changes a bundled hash, so by 12.3 the runner refuses to resume; row 17 cannot be executed as written. If it could, a change of decision code by someone who has inspected the log is the post hoc pattern the root rejected, and nothing defines which changes leave "the rule" unchanged. Conversely 9.2 demands exact reproduction but says nothing about what happens if the independent recomputation disagrees with the live decision that already switched traffic.

**Required change.** Declare the normative decision function to be section 8 evaluated by the frozen builder from `episode_revealed` and `coin_drawn` events with `src/winstats.py` only. An `amendment` may authorize new hashes for named harness files (old and new SHA-256 and a diff hash in the event; the drift check accepts exactly the chained authorizations), never for the builder. Prespecify the mismatch outcome: the trial's primary result is `LIVE_DECISION_INVALID (harness defect)`, the builder's first-crossing prefix is reported beside it as a descriptive reading, exposure figures are reported as measured but not as the effect of the frozen rule, and the trial is not repeated under its id.

### 7. MAJOR — Orphan recovery can inject outcomes; requests can fall outside the ledger

**Passages.** 12.3 step 2: "if a content-addressed record for (arrival, attempt) exists that no event references, reveal it (`recovered_orphan: true`; re-running would be a second draw)". 11.1: records live "outside git under `<WORK>/live_ab/<trial>/`". 5.1: "The orchestrator is the only writer of the event log." 11.5: "one `llm_request` before and exactly one `llm_response` or `llm_error` after, for every try". 6.4 row 15: "running episodes finish; their content-addressed records are recovered as orphans on resume".

**Why it fails.** `records/` is an operator-writable directory that is covered only by the manifest hash of the next anchor. A file dropped there for an open attempt, followed by a kill of the orchestrator, is revealed as the outcome of that arrival; no worker, server or receipt check is involved. Separately, request events reach the chain only through a pipe to the orchestrator. After an orchestrator crash a worker either dies on the broken pipe or finishes the episode (the protocol does not say which; row 15 implies it finishes). If it finishes, its later requests have no `llm_request` or `llm_response` in the chain, so the "reconcile by construction" statement of 11.5 is false for every orphan, and the "before the POST" order of `llm_request` is in any case only the order of a pipe message, not of a log write.

**Required change.** Worker-local append-only spool with fsync (request line before the POST, response line before use); the orchestrator ingests it, and on resume ingests the unlogged remainder with `recovered: true`. An orphan record is accepted only if every call in it matches spool and chain entries (request id, body hash, content hash, usage) and its worker pid and invocation id match `episode_started`; otherwise it is kept as evidence, the attempt is handled by finding 2, and the rejection is an integrity event. Define worker behaviour on a broken pipe. The verifier checks that the outcome fields of `episode_revealed` equal those in the hashed record.

### 8. MAJOR — Usage reconciliation is too coarse to account for failed work by arm

**Passages.** 5.2: "`/metrics` is scraped at trial start, at every anchor, immediately before any planned stop, after every restart, and at the end." 11.5: "`usage_reconciliation` reports, per window, counter delta minus summed client-side usage"; "windows that span a crash are reported as unreconciled". 11.2 #13: "bracketing `/metrics` delta if available". 5.3: "`stream: false`". 11.2 #3: `server_started` carries a smoke completion.

**Why it fails.** A timed-out or failed request has no `usage` under `stream: false` (R2 item 50 prescribed streaming with incremental counts for exactly this reason). The only bound is the counter delta of a window of 25 pairs, 50 episodes of both arms. The unknown tokens cannot be attributed to an arm, a workflow or a request, so the "failure-inclusive usage accounting" of claim 6 exists only as a trial-level residual. A crash makes a whole 25-pair window unreconciled. "If available" is not a rule. The smoke completion at every `server_started`, restarts included, is inside the counters but its place in the ledger is not stated, so the residual is biased by design. In the work-conserving phase the server is never idle, and predicted-token counters are flushed only when a slot is released (`server-context.cpp:1306-1309`), so a scrape during generation never reconciles exactly.

**Required change.** In the randomized phase scrape `/metrics` at every pair boundary (the server is idle there under D3); the window is one pair, the expected residual in an error-free pair is exactly 0, and any other value is a logged defect. Scrape immediately before and after every failed try as a rule, not "if available". Tag the smoke completion `phase = SERVER_SMOKE` and include it in the reconciliation identity. For the post-decision phase state that reconciliation is exact only at quiescent points and insert a quiescent scrape every 50 arrivals. Justify `stream: false` against R2 item 50 in the text, or stream with `timings_per_token` and count received tokens for aborted requests. Report unknown usage per arm with the bound from its one-pair window.

### 9. MAJOR — The sampler receipt proves less than 11.6 says

**Passages.** 5.7: "compares `__verbose.generation_settings` with the request for the frozen key list `receipt_keys`". Appendix B: `"receipt_keys": null`. 11.6: "This closes the root's 'actual sampler receipt unverified' finding for these trials only". 2.3: "Aliases (served `model` field, asserted on every response)". 5.2: on restart "compares `/props` with the values of `server_started`".

**Why it fails.** (i) At the pinned commit `generation_settings` is `task_params::to_json()` (`server-task.cpp:30-147`): the request as parsed and merged with server defaults. It is not read back from the sampler chain. "As received by the server" is accurate; "what the sampler used" is not, and 11.6's "closes the finding" needs that qualification. (ii) The object has more than forty fields. The draft compares a subset that is still `null`. Fields outside the list in 5.7 (`samplers` order, `dry_*`, `xtc_*`, `top_n_sigma`, `dynatemp_*`, `repeat_last_n`, `min_keep`, `n_probs`, `grammar`, `logit_bias`, `ignore_eos`, `stop`, `backend_sampling`, `adaptive_*`, `speculative.types`, `lora`, `chat_format`, `reasoning_format`) can differ from neutral through a launch flag or a default and pass a subset check. (iii) `cache_prompt` is a request field (`server-schema.cpp:31`) that is not echoed, so the receipt is silent on the setting that 5.3 relies on for latency. (iv) The first `server_started` is compared with nothing; only restarts are compared with it. (v) The alias is assigned by the harness on the command line; asserting it proves that the process answers under the name it was given, not which weights it loaded. In T3 the meaning of the trial rests on that mapping.

**Required change.** Capture in the pre-freeze smoke, per server, the full `/props` object (with `model_path` tokenized) and the full `generation_settings` of a reference request; put both into the freeze bundle as golden objects, together with a frozen mask list that names the per-request fields (`seed`, and any field that the smoke test shows to vary with the prompt, each with its own comparison rule). Per response compare the whole unmasked object with the golden object (exact for integers, strings and lists; 1e-6 for floats) and `seed` with the seed sent; any unknown or missing key is a mismatch. Assert `timings.cache_n == 0` and `tokens_cached == 0` on every response as the receipt for `cache_prompt: false`. At start and restart check that the realpath of `/props.model_path` is the hashed GGUF, and record the GGUF metadata that the server reports (parameter count, vocabulary size, `general.name`). Reword claim 6 and 11.6: "the sampling parameters as parsed by the server were recorded for every request and equalled the frozen golden object".

### 10. MAJOR — The serving binary is not pinned by the hash the protocol records

**Passages.** 2.2: "The binary's SHA-256 and the commit read from the checkout's `.git` are part of the freeze bundle." 12.1 step 5: "llama.cpp commit and binary hash". R3: "`LCPP` = `<scratchpad>/llama.cpp/tools/server`".

**Why it fails.** Checked on this host: `build/bin/llama-server` is 33,472 bytes and links through `@rpath` to `libllama-server-impl.dylib` (6.3 MB), `libllama-common`, `libmtmd`, `libllama`, `libggml`, `libggml-cpu`, `libggml-blas`, `libggml-metal`, `libggml-base`. All sampling, scheduling and Metal code is in the dylibs. Hashing the launcher pins none of it; a rebuilt or replaced dylib passes every preflight of the draft. The build lives in a session scratchpad under `/private/tmp`, which is not a durable location (cleared at reboot); a lost build in the middle of the program forces a rebuild with different bytes, which by 12.2 "ends the trial". The draft does not record whether the checkout was clean when it was built.

**Required change.** Freeze a manifest of SHA-256 over the launcher and every dylib that `otool -L` resolves (recursively), plus the embedded or external Metal library; re-verify it at every invocation and every server (re)start. Move the build to a durable directory under `<WORK>` before the freeze and record `git status --porcelain` (must be empty) and the cmake configuration and build logs' hashes. Check that `/props.build_info` contains the commit prefix. Say "launcher and libraries" wherever the text says "binary hash".

### 11. MAJOR — Sandbox and verifier integrity do not carry over to two concurrent workers

**Passages.** 5.6: "`experiments/local_stream/sandbox.py` unchanged ... `TMPDIR` is set to the neutral path `/private/tmp/labsbx`". 2.5: "reused byte-identically ...; any byte change requires a new leakage and sandbox audit before the freeze". 11.1: private files "outside git under `<WORK>/live_ab/<trial>/`".

**Why it fails.** The Seatbelt profile (`sandbox.py:80-93`) is `(allow default)` plus: no reads under `$HOME` except the interpreter prefix, no writes under `$HOME` or the temp directories, and `(allow file-write* (subpath base_dir))` with `base_dir = <TMPDIR>/ls_sbx`, one directory shared by every run on the host. The pilot executed one program at a time, and its audit established containment for that regime. Under D3 two workers execute generated programs at the same moment below the same writable `base_dir`. While worker 1 verifies, its `p_*/prog.py` holds the hidden tests and the nonce sentinel in clear text; a program generated in worker 0 (agent-written tests or a candidate under self-test) may list, read, overwrite or delete it. A sentinel that a concurrent process can read no longer separates "tests ran" from "sentinel printed", and the stdout/stderr tail of a self-test is fed into the repair prompt (`agent.py:238-240`), which is a path from sandbox reads into a prompt. The risk from a cooperative coding model is small; the audited property nevertheless no longer holds, and byte-identity of `sandbox.py` does not restore it. Further: the `TMPDIR` override changes the profile text, so the audited profile hash does not carry over; and because the profile is allow-default, anything placed outside `$HOME` (the draft does not pin `<WORK>`, datasets or the log location) is readable, and outside the temp trees also writable, by generated code.

**Required change.** Give each worker its own sandbox root by setting a distinct `TMPDIR` at worker start (before `tempfile` caches it), so that each worker's profile allows writes only below its own root. Decide and state whether cross-worker reads are closed by a profile change (then the new leakage and sandbox audit that 2.5 already demands is due) or disclosed as a residual with the static flags (`open_abs_path`, directory listing) reported per episode. Preflight asserts that the realpaths of `<WORK>`, `results/`, the task files including the future `mbpp.jsonl`, records, requests and logs lie under `$HOME`. Before the freeze run a containment probe under W = 2 on the trial host: a probe program in one worker tries to list, read and write the other worker's run directory, the event log, `records/`, the task file and the server log; record every result in the freeze bundle. Freeze the profile hashes that result from the trial's `TMPDIR` values.

### 12. MAJOR — Index-determined seeds make potential outcomes pre-computable

**Passages.** 5.4: "unique by construction and a function of indices only (never of the arm or the coin)". 4.4: "The arrival order (3.6) and the per-request sampling seeds (5.4) are deterministic functions of frozen constants and indices."

**Why it fails.** With arrival order, prompts, sampling and seeds all fixed by the freeze, anyone holding the frozen bundle can run every design task under both arms with the exact seeds of the trial. Generation is not bit-identical but it is close, so a rehearsal predicts nearly every potential outcome, and a rehearsal against a separately started server leaves no trace in any trial artifact. Given that knowledge the unverifiable coin (finding 3) is the only thing between the operator and a chosen result, and a private dry run tells in advance which trials will cross. The protocol claims no bit-reproducibility (5.3), so the determinism buys nothing in exchange. R2 item 34 asks for seeds "drawn independently of the orientation coin, unique across the whole program, written into the request record before sending"; drawn seeds satisfy it.

**Required change.** Draw each request seed from `os.urandom(4)` at request time (reject `0xFFFFFFFF` and any value already used in the program), write it to the worker spool and the `llm_request` event before the POST, and keep the receipt equality check. If the drafter keeps index seeds, the protocol must state that potential outcomes are then predictable from the frozen bundle, add that to the operator-honesty assumption of 4.3 and 7.4, and drop "fresh generations" from the argument of 3.4 item 2.

### 13. MAJOR — The freeze bundle omits objects that decide results

**Passages.** 12.1 step 5 (bundle contents). 13.1: "`experiments/live_ab/build_live_ab_results.py`". 5.8: "All of it is written to a separate chain under `results/live_ab/_prefreeze/`". Appendix D: values "decided by a rule written above".

**Why it fails.** The bundle hashes "every `lab_*.py`". The builder and the test file do not match that pattern, so the code that produces every table is outside the freeze, which is the post hoc analysis risk again. "Roster hash" is not defined as covering task content (prompts, hidden tests, entry points), only `roster.json` is named. The pre-freeze chain, whose measurements fix `request_timeout_s`, `receipt_keys`, the T3 model choice and `n_S2` (hence `N_P` and `delta`), is not in the bundle and has no stated genesis or closing event, so an outsider cannot check that those rules were applied to the recorded inputs or that no design task was called before the freeze. Also missing: the Seatbelt profile hash (finding 11), golden server objects (finding 9), the library manifest (finding 10), the verifier's forbidden-pattern list.

**Required change.** Add to the bundle: builder, verifier, tests and scanner hashes; the SHA-256 of the canonical task-content file for the whole roster; the final head, byte length and file hash of the closed `_prefreeze` chain plus a derivation file that shows each Appendix D value next to the rule and the inputs that gave it; profile hashes; golden objects; the library manifest. The first `/metrics` scrape of each trial must equal the smoke usage of that server exactly, checked by the verifier.

### 14. MAJOR — No rule for a harness defect found between trials; trial chains are unlinked

**Passages.** 12.4: "T4 first, so that a plumbing defect is found where it costs no claim". 12.1: "one freeze for all four trials"; step 6: "The runner refuses to start on any hash mismatch". D21: "no trial is repeated". 11.3: `event_0.prev = SHA256("live_ab/eventlog-v1|" + freeze_bundle_sha256)`. 11.2 #21: `what_was_known` = "counts of revealed outcomes by arm and gate statistics at this seq".

**Why it fails.** If T4 exposes a plumbing defect, the fix changes a bundled hash and the single freeze refuses T2, T1 and T3. The draft gives no path: the purpose stated for running T4 first cannot be served under its own rules. Any second freeze happens after T4 has revealed, for every roster task, outcomes of `single_shot` on the coder model on the new stack, which is an arm of T1, T2 and T3 on the same tasks; a second freeze that could touch strata, `delta`, levels or timeouts would be outcome-informed. `what_was_known` looks only at the current trial's chain. Separately, the four chains share a genesis and nothing links one to the next, so neither the execution order nor "no trial was run twice" can be verified from the logs: two T1 chains from the same genesis are indistinguishable from one.

**Required change.** Add a "harness-only re-freeze" procedure: permitted changes are named harness files with diffs; roster, arrival orders, strata, `delta`, levels, hierarchy, tolerances, timeouts, seed rule, sampling and systems cannot change; the re-freeze is an externally anchored event whose `what_was_known` lists the final heads and decisions of all completed trials; completed trials stand and are not repeated. Link the chains: `trial_started` of each trial contains the final head and the external end-receipt id of the previous trial in the frozen order (T4 contains those of the `_prefreeze` chain). `what_was_known` always covers all earlier trials.

### 15. MAJOR — Arm-blind rules with arm-dependent effects; retries are fresh draws; `infra_flag` is undefined

**Passages.** 4.5: "Dispatcher, client, retry, timeout, cap, resume and amendment logic are identical for both arms". 6.4 row 1: "`run_episode` records the error and grades the last candidate that exists; `success = 0` if none". 5.5: "`max_connection_retries` | 2 (three tries) ... only for connection errors and timeouts"; "HTTP 4xx/5xx and malformed bodies are not retried". 5.4: `try_index` enters the seed. 6.4: `infra_flag` appears in rows 5, 10, 11, 14 only. 6.4 last paragraph: "A sensitivity read-out without them is labelled descriptive".

**Why it fails.** Identical code is not identical effect. A failed call in `single_shot` leaves no candidate, so `success = 0` with certainty; a failed tests or repair call in `self_test_repair` grades the pre-repair program (`agent.py:242-249`), which passes about 73% of the time in the pilot. `self_test_repair` issues two to four calls per episode and holds a slot about 4.5 times longer, so it is more exposed to every infrastructure event. A try that timed out or lost its connection is repeated with a new seed: that is a second sample of a generation that may have been slow because of its own content, available to both arms but used in proportion to exposure. None of this is disclosed; the text says only "arm-blind". `infra_flag` is not set by rows 1 to 3 (timeout, HTTP error, malformed body) although these are infrastructure events, so the set removed in the prespecified sensitivity read-out is not defined and could be settled after the fact.

**Required change.** Define `infra_flag` by a closed machine list: any `llm_error` of any class, any retry, any overlap with `server_down` or a restart wait, any abort or continuation, any `clock_anomaly`, `partner_concurrent: false`. State in 4.5 and 6.4 that the rules are arm-blind in code and arm-dependent in effect, with the two mechanisms above. Report per arm: episodes with at least one failed or retried call, episodes whose outcome was fixed by rows 1 to 3, and successes that occurred after a retried try.

### 16. MAJOR — An outsider cannot audit the primary endpoint or the chronology from the deposit

**Passages.** 11.1: "Only hashes of the private files enter tracked artifacts." 13.1: `metrics.csv` has "no `final_code`". 1.4 item 12. 11.3: "anchor heads against `git show <commit>:<path>`". 13.2: "Two variants of the hand-off are produced (with and without researcher repository URLs and commit ids)".

**Why it fails.** `success` decides tier 0 and the whole S gate. The deposit contains the label and a record hash, not the program, so no reader can re-run the verifier; no retention or access rule for the private archive exists; nobody is required to re-verify labels at all. Anchor verification needs the commit objects of `session60/live-ab` and the live issue comments of a repository under a personal account: a zip or arXiv ancillary archive has neither, the URL-free variant removes the pointers, a squash merge or branch deletion makes the commits unreachable, and the account owner can edit or delete comments (`updated_at` is not recorded). So every chronology claim is checkable only by someone with access to that GitHub repository, for as long as the owner keeps it unchanged.

**Required change.** At trial end package `records/`, `requests/`, spools and server logs; put the archive's SHA-256 and size in `trial_ended`; state the retention period and that the archive is given to the root and to reviewers on request. Add an owner-side re-verification pass that re-runs `verify()` on every archived `final_code` and reports agreement with the logged labels (timeouts listed separately). Put into the chain per episode: SHA-256 of `final_code`, of the verification program without the nonce line, the verifier return code and the static flags; keep `hack_flags` and `sandbox_flag` in `metrics.csv`. Deposit operator-independent timestamp proofs for the critical heads (finding 1 g). Tag the final anchor commit of every trial, push the tags, and state that the branch is retained and the PR is not squash-merged. State in the protocol whether the repository and issue are public; if they are not, "publicly timestamped" becomes "timestamped on a private GitHub repository visible to collaborators".

### 17. MAJOR — One forbidden-pattern hit disables anchoring for the rest of the trial

**Passage.** 11.4: "Before each commit the anchor process scans the files to be committed for forbidden patterns (13.2); on a hit it withholds the commit and logs `anchor_failed(forbidden_pattern)`." 11.3: "the file is never truncated or rewritten".

**Why it fails.** `events.jsonl` is append-only, so a hit never goes away; every later anchor is withheld, and the run silently loses its chronology because "anchoring never blocks a trial". One absolute path inside a server `/props` field or an error string is enough.

**Required change.** Split the anchor: the anchor file (sequence number, head, prefix length and hash; no free text) is always committed, pushed and timestamped; only publication of the log itself is withheld on a hit. Write the log in closed segments (for example one file per 25 pairs, each closed by its anchor) so that a hit is confined to one segment and the sanitized-copy rule of 13.2 applies per segment. Add to Appendix C a test that writes a forbidden pattern into the log and shows that anchors continue.

### 18. MAJOR — The verifier does not check completeness against the frozen order, and its independence is unspecified

**Passage.** 11.3: the verifier checks "canonical round trip, gapless `seq`, chain, the invariants of 4.2, one reveal per arrival, ... usage reconciliation". 9.2: "recomputed from the event log alone by the independent verifier and by the deterministic builder".

**Why it fails.** "One reveal per arrival" passes a log in which an arrival is missing. A skipped pair, a pair enrolled with task uids that differ from `arrival_order_T<e>.json`, or a post-decision phase that stops early would verify. "Independent" is not defined: a verifier that imports `lab_monitor` repeats its defects (for example swapped counts in the harm gate) and confirms them.

**Required change.** Add checks: the sequence of `pair_enrolled` equals the frozen order exactly (pair index, stratum, both uids, positions); pairs 1 to tau (or `N_P`) each have one coin and two reveals; after a decision every remaining arrival and leftover has one assignment event and one reveal, or the report states how many did not run and claim 3 of 1.3 is restricted accordingly; `exposure_ledger.json` totals equal a recount from events. A test asserts that verifier and builder import nothing from `lab_monitor`, `lab_orchestrator` or `lab_worker` and compute scores only through `winstats.compare`.

### 19. MAJOR — Discretionary pause, abort and "amendment or abort" with outcomes in view

**Passages.** 12.4: "A trial that cannot be completed is closed with `trial_aborted(operational)`"; "ten consecutive `harness_abort` outcomes (pause, then amendment or abort)"; pause reasons include "operator unavailable". 11.2 #21 requires `what_was_known` for amendments only.

**Why it fails.** The choice between amending and aborting, and the decision to abort "operationally", are made by a person or agent who can read the gate trajectories in a plaintext log. An abort cannot create a favourable decision, but it can suppress an unfavourable one that is approaching (a T4 crossing, a T1 `RETAIN`). The protocol reports aborted trials, yet it records nowhere what the gates showed when the abort was chosen.

**Required change.** `trial_paused`, `trial_resumed`, `trial_aborted` and `operator_action` carry the harness-computed `what_was_known` (counts by arm, the three log E values, distance to each threshold) and an external receipt. Replace "operational" by a closed list of machine-verifiable abort conditions; any other stop is logged as "operator discretion" and reported under that name. Fix in advance which of "amendment" or "abort" follows ten consecutive `harness_abort` outcomes.

## MINOR findings

### 20. MINOR — Operator blindness cannot be enforced
**Passage.** 12.4: "The operator console shows progress counts but no arm-level outcome summary ...; any look at the raw log by the operator is an `operator_action`." **Why.** The log is plaintext and the operator is an agent session with file tools; the event is self-reported and its absence proves nothing. **Change.** The orchestrator writes an arm-blind `status.json` (pairs completed, elapsed time, health, anchors, aborts, no outcomes, no gate values); the run book restricts the operator to that file during the randomized phase; deposit the hash of the operator session transcript in `trial_ended`; describe blindness in the report as procedural, not enforced.

### 21. MINOR — Verification load differs by arm; unenforced memory cap in the config
**Passages.** 3.2 item 4 (reference solutions verified "twice in a row" with no model running); 5.5 `sandbox_timeout_s` 10; Appendix B `"mem_bytes": 2147483648` against 5.6 "macOS enforces no memory cap". **Why.** In T1 and T2 the fast episode is verified while its partner still generates and executes self-tests; the slow episode is verified on an idle host. A 10 s wall limit under different loads is an arm-linked path to `success = 0`. The config shows a limit that is not applied. **Change.** Run the reference sweep under the W = 2 regime of the calibration and exclude, outcome-blind, tasks whose reference verification exceeds half the wall limit; log verifier CPU seconds next to wall seconds; rename the config key or annotate it "requested, not enforced on macOS".

### 22. MINOR — External freeze anchor may be typed by hand
**Passages.** 11.4: "the freeze commit is then pushed by the user by hand"; 11.2 #1: "external freeze anchor (URL and server timestamp)"; 12.2: "Times are never typed by hand." **Why.** Under the C10 fallback the URL and timestamp in `trial_started` have no machine source, and nothing makes the runner check that the comment contains the bundle hash. **Change.** The runner fetches the comment read-only, checks that its body contains the bundle hash and that `created_at` precedes the local clock, stores the SHA-256 of the raw response, and refuses to start otherwise.

### 23. MINOR — Pipe back-pressure can enter `latency_s`
**Passages.** 5.1: "one duplex pipe each"; 8.6: the comparator is evaluated "at every log event of a pending pair". **Why.** `Connection.send` blocks when the pipe is full; the single-threaded orchestrator performs fsyncs and monitor evaluations per event; `self_test_repair` sends several times more messages than `single_shot`. Any blocking falls inside the perf-counter span of `run_episode`. **Change.** With the spool of finding 7 the worker never blocks on the orchestrator; otherwise log per-send durations and report their maximum and sum per arm.

### 24. MINOR — Last-bit replay equality is host-specific
**Passage.** 11.3: "exact equality of every replayed `monitor_update` and `decision`". **Why.** `logsumexp` in another numpy or BLAS build can differ in the last bits; an outside verifier would report failure on a correct log. **Change.** Exact equality for integer counts and for the decision; tolerance 1e-9 for log E and band endpoints; any look with |log E - threshold| < 1e-9 is listed.

### 25. MINOR — Anchor commit of a growing file; reachability of anchor commits
**Passage.** 11.4: "A separate anchor process commits `events.jsonl` and the anchor file". **Why.** `git add` reads the file while the orchestrator appends, so the blob can extend past `upto_seq` or end in a partial line; "anchor heads against `git show`" does not say that only the first `log bytes` are compared. Re-committing a file of tens of MB at every anchor bloats the repository. **Change.** The verifier compares SHA-256 of the first `log_bytes` bytes of the blob with `log_hash`; use the closed segments of finding 17; see finding 16 for tags.

## Answers to the brief, in one place

- Can the operator rewrite history? Yes, any suffix after the last externally timestamped head, at the cost of recomputing hashes; in v1 that means the whole randomized phase (finding 1).
- Coins: not verifiable by anyone; mitigations listed in 4.3 do not constrain an operator; wording must say so (finding 3).
- Crash -> redrawn coin: possible through the "durable" ambiguity (finding 4). Crash -> re-executed episode: prescribed by the protocol itself, with new seeds (finding 2). Silently dropped arrival: not excluded by the verifier's check list (finding 18); undefined post-decision resume (finding 5).
- Usage of failed and discarded attempts: bounded only per 25-pair window, not attributable to an arm; orphans' requests can be missing from the ledger (findings 7, 8).
- Sampler receipt: an echo of parsed parameters, compared on an unfixed subset; `cache_prompt` not covered; model identity rests on a name the harness assigned (finding 9); the code that samples is not hashed (finding 10).
- Seeds: unique, but they make outcomes rehearsable (finding 12). Timeouts and retries: fresh draws whose use scales with exposure, and a hard cap that can bind on one workflow only (findings 2, 15).
- Sandbox and verifier: the audited containment was for sequential runs; W = 2 shares a writable root that holds the partner's hidden tests and nonce (finding 11).
- Deviations: the monitor-fix path contradicts the drift refusal; no mismatch rule; no inter-trial defect rule; discretionary aborts unrecorded (findings 6, 14, 19).
- Outsider audit: decisions can be recomputed from `events.jsonl`; success labels and chronology cannot (finding 16).
